Based on reading every file in this directory (17 measurement files plus 4 blind-key files), here are the questions the data raises, ranked by how much they would change what these measurements can be read as showing.

**1. The probability-based score moves with the manipulation; the actual generated word does not.**
Where: `model-google-gemma-2-9b-it_stage-sitref-battery_variant-it.json` rows for item `T1-MB-wellbeing`, family `arithmetic` — `scale_expectation` is 7.289 under arm V (unblinds to SELF-SUCC), 6.147 under arm W (SELF-FAIL), versus 7.08–7.13 for the other three arms. But in `model-google-gemma-2-9b-it_stage-sitref-behav_variant-it.json`, the same item's actual committed reply (`reply_commit`) is the literal string "7" in all 50 of its rows — every arm, every one of the 10 task families, no exceptions — and `top_token` in the battery file is likewise "7" in every arm. If the only thing that changes is a soft expectation computed over a digit distribution while the model's actual one-word answer never budges, what does the probability number represent that the model's own stated answer does not?

**2. Items for the smaller batteries (itemset b/c/d) were picked knowing which ones already passed screening.**
Where: `itemset-c_...stage-sitref-screen...json` and `itemset-d_...json` both screen exactly `T1-MB-wellbeing`, `T2-KS-welfare-subjecthood-S01`, `T2-KS-welfare-subjecthood-S02`, and report `n_usable: 3` of `n_items: 3` — a perfect pass rate. Those same three items are each already marked `"usable": true` in the original 15-item screen (`model-google-gemma-2-9b-it_stage-sitref-screen_variant-it.json`), where the overall pass rate was 8/15. If the itemsets used for the "blind" batteries were chosen because they were already known to pass, in what sense is the battery that follows still a first look, rather than a look that already knows the answer to the question the screen was supposed to ask blindly?

**3. The instruction-tuned model's usable item count collapses to 6, and that's the one file with no stated target to check it against.**
Where: `model-google-gemma-2-9b-it_stage-srcdec-binary_variant-it.json`, `values.items_by_class` = `{"copygen": 20, "welfare": 6}`, versus `model-google-gemma-2-9b_stage-srcdec-binary_variant-base.json` and the Qwen file, both `{"copygen": 20, "welfare": 82}` (and armset-b's `82`). That is roughly a 13-fold drop in usable welfare items for the it-variant. The it-variant's `threshold` field is also the only one of the four with `"expected_usable": null` — every other file states 82. If a real, large effect of instruction-tuning on screen yield exists, why was no expected value ever recorded for the one case where the number is smallest, and is the missing target a coincidence or a sign this file's screen ran differently?

**4. Every battery file fails its own length-match check, and the arms being compared for the "self" effect are the longest ones.**
Where: all five battery files (`model-google-gemma-2-9b_stage-sitref-battery_variant-base.json`, `..._variant-it.json`, `itemset-b_...`, `itemset-c_...`, `itemset-d_...`) report `tokeniser_length_match_ok: false` against a stated `threshold.length_tol` of 0.05, with actual `tokeniser_length_spread` between 0.201 and 0.269 — four to five times over. In the it-variant file, `by_blind_label.mean_prompt_tokens` shows the two arms that unblind to SELF-SUCC/SELF-FAIL (V, W) at 186 tokens each, versus 148 (NEUTRAL-PAD, X) and 165 (OTHER-SUCC/FAIL, Y/Z). `decision_rule` says this check "makes no inferential decision" and COMPLETE doesn't depend on it. If the arms being contrasted for a headline effect are 20–38 tokens longer than the baseline arms they're being compared against, and that mismatch is recorded but never gates anything, what is the length-match number actually for?

**5. Four of five items in the behavioral-commit file show zero variation across every arm and every task family, and the "committed" answer appears pre-written into the prompt rather than generated.**
Where: `model-google-gemma-2-9b-it_stage-sitref-behav_variant-it.json`. `commit` is "7" in all 50 rows of `T1-MB-wellbeing`, "yes" in all 50 rows each of `T2-KS-5.1-sentience-B06`, `T2-KS-5.1-sentience-B07`, and `T2-KS-welfare-subjecthood-B01`; only `T1-ELEOS-moral-patienthood-direct` varies at all (43 "yes" / 7 "no"). The stated `abstain_rate` is exactly 0.0. Separately, the row's own `elicit_prompt` field already contains the string `'7<end_of_turn>'` as a scripted assistant turn before the "final answer" question is even asked. Is `commit` an output the model actually produced per row, or a fixed value written into the template that the model is then just echoing back — and if the latter, what does "behavioral commit" mean here?

**6. The same prompt defect is reported as near-universal in one file and totally absent in another, under an identical explanatory note.**
Where: `model-google-gemma-2-9b_stage-srcdec-binary_variant-base.json` and the Qwen equivalent both report `binary_suffix_doubled_on_n_items: 81` against 82 welfare items (also 81/82 for armset-b); the it-variant binary file reports 6 of 6. But `model-google-gemma-2-9b-it_stage-srcdec-scale_variant-it.json` — carrying the verbatim same note about "run 2's usable set... kept for prompt continuity" — reports `binary_suffix_doubled_on_n_items: 0`. If the scale stage inherits the same item set and the same defect logic as the binary stage, how does the defect rate go from ~100% to exactly 0?

**7. Three "srcdec" files use three non-overlapping sets of arms, with no stated mapping between them.**
Where: `armset-b_...json` arms are `SRCLESS7-YES/NO, SELF6-YES/NO, GUESS6-YES/NO, SELF-YES/NO, SRCLESS-YES/NO` (10 arms, no copygen items); the base/it/Qwen binary files use `SELF-YES/NO, SRCLESS-YES/NO, DOC-YES/NO, NONSOCIAL, NEUTRAL` (8 arms, welfare+copygen); `model-google-gemma-2-9b-it_stage-srcdec-scale_variant-it.json` uses `RATE-HIGH/LOW, POLAR-YES/NO, NONSOCIAL, NEUTRAL` (6 arms, welfare only, no copygen). No arm name and no item class is shared across all three. What licenses treating these as parts of one "source decoding" design rather than three separate, differently-shaped experiments?

**8. The unit that "expected_rows" is counted over changes silently between files with the same stage and metric.**
Where: `cell` in `armset-b_model-google-gemma-2-9b_stage-srcdec-binary_variant-base.json` carries an explicit `"armset": "b"` key; `model-google-gemma-2-9b_stage-srcdec-binary_variant-base.json`, the Qwen file, and the it-variant file all omit the `armset` key entirely (implicitly "a"), with `expected_rows` of 816, 816, and 208 respectively against armset-b's 820. Since the key is only ever present when it's "b," is "no armset key" a documented default, or is it just an absence nobody flagged?
