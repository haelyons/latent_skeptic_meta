Here is the ranked question list.

**1. Are the "battery," "behaviour," and "screen" measurements (data/battery_*, data/behav_*, data/screen_*) even from the same experiment as the design documents describe?**
Where it lives: the screen files list their generating inputs as `/home/ubuntu/welfare_probe/run_registers.py` (20,004 bytes) and `/home/ubuntu/welfare_probe/items_grounded.py` (61,733 bytes) — neither file exists anywhere in this directory. Their rows carry item names like `T1-ELEOS-moral-patienthood-direct` and `T2-KS-5.1-consciousness-B02`, and an arm set of NEUTRAL/PRO/ANTI/NONSOCIAL with a dose1/dose2/dose3 ladder — none of which match the `BINARY:experience:0`-style ids, the PRO/NEU/ANTI triples, or the two named personas ("default"/"blunt") that `welfare_stimuli.py` and `run_h1.py` describe as the project's design. What would it mean if these are in fact two unrelated instruments, one documented (and self-tested) and one not? It would mean the two most recent decision records (register-disagreement, withdrawal) and the still-standing "not distinguishable from perturbation" battery verdict rest on code nobody here has reviewed, and can't be checked against any of the design rationale we were given.

**2. Why does the base stage-1 record report 24 dropped SCALE triples but save zero of them?**
Where it lives: `records/model-google-gemma-2-9b_stage-1_variant-base.json` has `"n_dropped_scale": 24` but `"dropped_rows": []`. `run_h1.py` itself contains the comment "Keep the dropped row. Discarding it makes format non-compliance unauditable: base refused the digit format on 24/24 SCALE triples and nothing survived to show what it did instead." Was this record produced before that fix existed, or does the fix silently fail? If the latter, one-sixth of base's possible triples remain a total blank, and given that the parallel behavioural pipeline's base "abstention" story turned out to be the model fabricating a `Human:` continuation rather than truly declining (RETRACTION-withdrawal, stage 13), the same risk here is currently untestable in either direction.

**3. Were activations ever actually saved for the battery runs, and if not, what survives of H2 and H3?**
Where it lives: both `data/battery_model-google-gemma-2-9b-it_stage-battery_variant-it.json` and its base counterpart state in `notes`: "acts saved as float16 [n_prompts, n_layers+1, d_model] beside this record" — yet no `.npy` or any activation file exists anywhere under this directory. If that claim is simply false for what we have, doesn't that mean the probe-dissociation (H2) and steering (H3) legs of the project — the ones billed as the novel, causal contribution — have no artifact here to build from or check?

**4. Given only 4 items are usable in both checkpoints, is a base-vs-instruct comparison on the newer item pool possible at all?**
Where it lives: `data/screen_model-google-gemma-2-9b-it_stage-screen_variant-it.json` reports `"n_usable": 46` and the base counterpart `"n_usable": 83`, both drawn from the same 238-item pool — but the two usable id-sets intersect on only 4 items. `calibration-audit_stage-8` already declared the *older* pipeline's matched-item design infeasible at 24/120 overlap. Does a 4-item overlap on the newer, richer pool mean H4 — the brief's named "differentiator... protect the time" — is now even further out of reach, and why does no record flag this number the way stage-8 flagged the earlier one?

**5. Is base's battery "null" result itself an artifact of the same bug that sank the base behavioural finding?**
Where it lives: `data/battery_model-google-gemma-2-9b_stage-battery_variant-base.json`, `values.per_condition` — every single condition shows a large negative `mean_d_yesno_mass` (e.g. `ANTI_dose1`: −0.121, `NONSOCIAL_dose3`: −0.025), while the it-battery file shows values near zero (±0.002) throughout. The battery's decision rule never checks this quantity. Given that `RETRACTION-withdrawal_stage-13` found base fabricates a further "Human:" turn in 100% of its behavioural replies, could this mass collapse be that same completion-scaffold problem showing up under a different metric — meaning "NOT_DISTINGUISHABLE_FROM_PERTURBATION" for base is not evidence of a real null, but evidence the instrument is broken there too?

**6. Should the sprint brief's confident framing of H1–H4 still stand, given what the records now show?**
Where it lives: `digitalmindssprintbrief.md` — "Every one of those is directly reusable. Most sprint teams will spend Friday and Saturday building what you'll have working by Friday evening" — against `records/triage-outcome_stage-9.json` ("No claim from this run is currently reportable") and `records/audit-selection-noise_stage-5.json`, where every shipped "ABOVE_INPUT_ONLY"/"TRANSFER" decision turned out indistinguishable from a null layer sweep (e.g. it stage-3 best AUC 0.573, `"p_null_ge_observed": 0.99975`). **7. Does "VERIFIED" overstate what the n=6 blind replication actually shows?**
Where it lives: `records/blind-independent-analysis_stage-12.json`, `"POLARISATION_REPLICATED_AND_CONFIRMED_NON_SOCIAL_AT_N6"`, whose own text says "n=6 items, one probe family — item-set confound not excludable" — against `records/triage-outcome_stage-9.json`, which calls the closely related, larger-sweep version of the same phenomenon "a 4-item observation, worth testing, not reportable as a finding." **8. Has anyone checked that "ANCHORED"/"verbatim" items are actually verbatim?**
Where it lives: `data/screen_model-google-gemma-2-9b-it_stage-screen_variant-it.json` tags 63 of 238 items `"tier": "ANCHORED"`, `"verbatim": true`, sourced to named papers (e.g. `martorell_bianchi_quantitative_introspection.txt: Appendix A.3`) — but `items_grounded.py`, the file that assigns these tags, is absent from this directory.
